# TechSpec maintenance

Use `harness-product-techspec` after idea/document intake or a code/contract change. Apply Core artifact-contract before selecting canonical storage and Core adaptive-verification before runtime claims. Requirements, scoped code/contracts and evidence jointly inform the draft; approved SRS intent must not be silently rewritten to match code. If sources conflict, record both revisions and establish the authoritative source/owner decision before changing disputed behavior.

For new docs clarify unknown storage, then scaffold only missing documents. For existing docs inspect observed revision and propose affected sections with before/after contracts and artifact-impact. External Confluence/Jira/Figma/database connections remain host-dependent aliases under existing integrations.json, with no new configuration or provider runtime. Recheck actual permission and source-write policy before writes. Return a reviewed patch/publication receipt or a precise BLOCKED handoff; never overwrite or merge automatically.

Use Core `continuous-development.md` for every resume: recheck revisions immediately before section writes, reconcile concurrent edits and invalidate affected stale evidence. Preserve stable IDs and unrelated sections; a proposed patch is not canonical publication.

For grouped/long-running checks use Core `.notth/core/workflows/recoverable-verification.md`. Save actual observations and proposed section updates incrementally, use existing checkpoints with evidence hashes, reconcile process/side-effect ownership on resume, and rerun affected groups after baseline changes. Keep the procedure independent of stack, domain and host.
