# OpenSpec integration

The initial integration uses the upstream `spec-driven` schema, project context and artifact rules.
It does not fork OpenSpec, bundle its CLI or implement its archive/sync engine.
Install and pin OpenSpec with the package manager and runtime requirements appropriate to your project.
Consult upstream installation instructions; no floating `latest` dependency is injected into consumers.

The harness new-change command creates `.openspec.yaml`, proposal.md, design.md, tasks.md and
specs/<change-id>/spec.md. Replace draft TODOs and use capability names that match your actual domain;
the change ID is only a default capability slug. For changes to existing behavior use MODIFIED/REMOVED
delta sections as required by upstream. Keep acceptance criteria observable.

Use upstream `openspec validate <change-id> --strict` before review. Tool-specific slash commands are
not hardcoded; use the integration generated by your pinned OpenSpec version if needed.
Archive/sync is performed through OpenSpec only after all related PRs merge. Archive status is change-specific; a created PR or checked task does not prove merge.
No agent or CLI automatically checks off the archive task.

Upstream references consulted 2026-10-10:
- https://github.com/Fission-AI/OpenSpec/blob/main/docs/customization.md
- https://github.com/Fission-AI/OpenSpec/blob/main/docs/cli.md

Compatibility limitation: templates were checked against documented structure. The upstream executable
is not a dependency of the offline CLI tests; running its validator is a separate verification step.
